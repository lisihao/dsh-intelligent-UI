# Source-bound executable component selection

## Compiler and decision boundary

The experimental block switch remains off by default and shares its configurable shortcut with DIL execution. Enabling it does not enable Jev Engineering, install another plugin, change the selected conversation model, or grant component actions tool authority.

The compiler parses the supplied content and builds source-owned blocks. Each registered component has one exact ID, one renderer key, an input validator and a source binder. Binding determines whether the current block supplies the facts and runtime prerequisites needed by that component. Ordinary prose and code are not assigned a fixed renderer beforehand. Markdown, structured organization and appropriate rich components can coexist as candidates.

The first Jev phase chooses reading frame and style; it does not ask the old per-block presentation/runtime questions that the component phase would replace. The complete local source recipes remain available to the component binder. Jev then selects a family and a concrete component. Large groups use stable partitions, with complete member metadata shared once per decision wave. Partitions do not rank or discard components. The coordinator validates the returned IDs and request freshness, then binds and dispatches the selected exact ID. It does not hand an `auto` answer back to older inference rules, invent missing component data or substitute another selected renderer after a component-stage failure.

## What all-components reachability means

All executable IDs enter the same registry; eligibility is per source block. A table is not a live feed, prose does not imply an approval queue, and a missing user action is not permission to run a tool. Components that need a source snapshot, source image, original model bytes or local handler remain unavailable until those inputs actually exist. Their exclusion reason remains explicit. There is no diversity quota, current-theme preference in automatic mode, hidden top-K filter or reward for decorative complexity.

Native table and list candidates preserve their inline Markdown through the host renderer. Numeric chart candidates reuse validated source mappings rather than estimating values. A native list route that cannot preserve a non-default starting number or task state is excluded. Source text, complete original records, units, qualifications and meaningful order remain accessible.

The same-ID registry covers the native DIL vocabulary, source composition recipes, four maintained animation/chart libraries, 15 curated material-role adapters, the complete pinned Uiverse archive, TuffUI entries and Canvas routes. Theme selection remains independent of component identity. Availability claims require the corresponding built consumer and its input contract, not a catalog label alone.

## DIL authoring and discovery

`solar_ui_catalog({format:"dil"})` returns the DIL guide and the registered executable metadata. `solar_ui_catalog({componentId:exactId})` returns that component's actual source/prop/event contract. A model may then use the native `<component id={exactId} input={sourceBoundJson} onChange={localHandler}/>` bridge. The Host generates frame mounts, nonces and transport authority; they are not authored inputs.

JSON fields containing source code, URLs or protocol examples remain data. The generic bridge checks bounded JSON, while each fixed consumer checks its exact schema. It does not interpret arbitrary JSX/HTML/CSS supplied as a component implementation.

TuffUI callbacks, Uiverse events and curated controls return only through explicitly supplied local DIL handlers. Editing local state does not call a model or submit a conversation. Explicit DIL form submission retains the existing normal continuation path and indeterminate-send protection.

## Runtime isolation

Rune uses the original pinned Rust/Wasm renderer for its owned material canvas, with semantic DOM content above it. TuffUI uses an opaque React 19/Tailwind 4 frame while DSH keeps React 18. Their fixed public bundles are verified by manifest path, size and SHA-256 before serving from a loopback capability URL. Uiverse uses fixed-source Shadow DOM with source-bound semantic text, CSS content, SVG text, fields and images. Canvas keeps its separate original-factory lifecycle and visible source.

Failures retain readable source and a named diagnostic. These mechanisms do not themselves prove installed Desktop support or visual fidelity; source, browser, model and installed-app evidence are reported separately.
