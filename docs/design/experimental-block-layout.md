# Experimental source-bound block layout compiler

This experiment addresses the whole-document selection boundary observed in the five-file Markdown review. It is opt-in and defaults to disabled when its saved setting is absent. It is a source development feature, not an installed-app or real-model acceptance claim.

## Contract

The pipeline is source parsing → compiler-owned block references and eligible candidates → one scoped Jev Decisions request → exact-choice and source validation → existing renderers. Jev chooses registered presentations; it supplies no rewritten source, new metrics, graph relations, HTML, CSS or JavaScript.

`adaptive.blockLayout` controls the entire compiler path. The existing `adaptive.enabled`, takeover and Jev feature gates still apply. Turning the experiment off restores the existing whole-output selection path and prevents an old compiled response from being adopted. `adaptive.blockLayoutShortcut` stores a configurable keyboard binding; its default is `Alt+Meta+KeyI` (Option + Command + I). A shortcut change alone does not change the decision fingerprint. Keyboard handling is client-owned and disposed with the plugin.

## Composition levels

The document retains one coherent theme and a reading frame. Each source-owned block can choose an eligible presentation and component set. A source table can stay a table, supply a historical chart or become a task board only when the existing analyzer validates the corresponding source contract. Explicit relationships may use the existing React Flow path. Loading, short text updates, live series, illustrations and object effects retain their existing input and browser requirements.

Research inspection is separate from the reading frame and block decisions. It must not suppress a neighboring flow, table, heading navigation or chart. Its option description explains that it adds report-local inspection and does not independently verify sources or execute AI organization.

The compiler targets bounded top-level source units. It splits prose at the finest source-heading depth that fits the complete block budget, and falls back to complete parent sections when necessary. Adjacent prose without a source heading may share a block, but is never excluded from selection. Every unit, including ordinary prose and code, receives an explicit presentation question. `reading`, `cards` and `disclosure` are executable source-bound treatments; validated data adds concrete table, chart, board, record or flow recipes. A choice is a complete renderer recipe, rather than an `auto` instruction to run the previous heuristic selector. Source nodes and document-scoped definitions retain their source references. A registered organization recipe may arrange eligible sibling list items inside that block; the model does not independently rewrite or select each sentence.

Experimental continuous reading groups intact source blocks into Paper chapter/figure regions. It does not apply the legacy paragraph-to-caption rearrangement inside an already selected block. The nonexperimental Paper transform is unchanged.

Markdown is rendered from the complete source document. Compiler offsets use UTF-16 positions matching the Markdown AST, not separately reparsed text fragments. Reference definitions and footnotes therefore remain document-scoped. Normalized tool text blocks use a source path as well as local Markdown offsets. Table eligibility is derived from the complete Markdown analysis and bound back to the exact source table, so nearby units, comparison prohibitions and section boundaries are not lost when identifying a block. Unrecognized content remains readable; source order, source strings, units and qualifications remain available.

## Candidate boundary and explanations

Candidates come from executable adapters with a normal rendering consumer, validated against actual source and runtime capabilities. The catalog's development archive, metadata-only items and blocked effects do not become executable merely by appearing in the catalog. Existing installed themes and compiled component sets remain available subject to user locks and compatibility. Every block wrapper supplies a compiled ThemeCard consumer. Automatic style mode offers native, soft-relief, clear-glass and mechanical-outline material per block; selected style mode retains the user's manual material lock. Theme packages remain selectable through the global theme question; an ASCII chart recipe may explicitly bind a compatible local ASCII theme. Irregular or gapped time series retain a renderer that preserves their original spacing and gaps; incompatible general-chart choices are not offered for those blocks. This is not a claim to automatically run every archived Uiverse or Canvas component.

The experimental registry also covers the 14 existing Canvas HTML effects, the isolated Bend/Hex Float interfaces and Particle Scroll through an actual source-bound consumer. These are optional visual copies beside a complete visible source, not replacements for text, code or data. Eligibility requires bounded noninteractive source, browser support, no streaming and no reduced-motion restriction; Magnify additionally requires explicit text-free decoration. Unsupported geometry/resources and execution errors remain visible. Metadata-only Canvas entries remain excluded. Object effect eligibility uses supported assets and actual renderer requirements; the old coding/project-management domain recommendations do not prohibit a model's explicit selection.

Local failure defaults and executable recipe metadata stay in the coordinator. The experimental model context contains exact source references and explicit question bindings, including each block’s independent component-set question; descriptions are supplied in the authoritative questions. Every option carries its complete description in every question; a 2026-11-07 change that moved repeated option guidance into shared state was reverted after live runs showed it shifting material choices ([record](../acceptance/2026-11-07-shared-option-guidance.md)). The frame request's `blockLayout` context and the component requests' input (`source-block-component-context@1`) also carry a `block-outline@2` outline: the top-level Markdown heading tree and numbered bold-only paragraphs used as headings (with a derived depth), with ranges and parent ids, and the innermost section of each compiled block. Local executor placeholders are not model constraints or recommendations. A pure-prose document may use source sections for continuous reading, and a long document may expose its complete heading index; the old mixed-media and 100-heading recommendation thresholds remain confined to the nonexperimental path.

The model receives descriptive affordances and tradeoffs rather than reason codes alone. Returned identifiers are checked against the exact questions sent. Singleton capability axes are filled locally; presentation choices for prose and code are never singleton or pre-fixed. Experimental model questions contain no `auto` option. Missing or invalid model choices are errors, not successful heuristic decisions. Every block reference is compiler-owned and is bound to the complete source revision and saved settings. Invalid, stale, unsupported or over-limit programs retain the local source view and surface a reason; they do not trigger an automatic paid retry.

The view can show the selected block adapter and local eligibility evidence. These explanations are generated from recorded source/candidate facts, not represented as textual reasoning returned by the Decisions API. Evaluation checks suitability and source coverage, not artificial diversity across five files.

## Verification boundary

Focused tests cover disabled compatibility, mixed-block candidates and rendering, exact source references, invalid choices, batched requests, stale-setting rejection, shortcut handling and durable settings. The final source gate and browser observations are recorded separately from any real Jev or official Desktop acceptance. No account, saved Jev route or installed plugin is changed by development tests.

## Content-fit Decisions input

The experimental request separates source eligibility from design suitability. Eligibility remains a compiler/runtime constraint; the decision prompt compares source fidelity, reading and scanning, navigation, explicit relationships, information density and interaction cost. There is no style-diversity target, novelty reward or locally adjusted model score. Continuous reading and native controls remain valid choices.

In automatic style mode, the current display theme is not supplied as a preference. Theme and material options describe their own visual characteristics, suitable reading tasks and limitations in the question itself. Selected style mode retains the saved theme/component lock. The experimental model context retains the complete original source and exact block references; the authoritative question list is sent once, without duplicating the catalog, local defaults or recipe execution placeholders in the input. The executor keeps the full candidate bundle for validation and rendering. Disabling the experiment retains the existing whole-output request path.

Provider probabilities and confidence are preserved as returned. They are not a calibrated measure of reading quality and do not override the returned choice. Local suitability descriptions explain the renderer and its source contract; they must not be presented as textual model reasoning.

## Source-preserving visual organization

Factual fidelity and visual arrangement are distinct. Facts, values, units, qualifications, uncertainty and source identity cannot change; the complete original remains available. Registered views may group explicit status records, arrange unordered source items, project validated numbers, and lay out explicit relationships. Meaningful procedure/time order remains authoritative. Navigation and column labels describe the interface and do not add factual claims.

The experimental `source-list-grid` recipe arranges eligible complete unordered source items into responsive per-item regions. `source-label-table` organizes explicitly labelled source items into label/detail rows. They retain the original item nodes and non-list content, links, footnotes, code and qualifications, with source-range mappings. They do not summarize prose, invent labels or create a relationship merely because entries appear side by side. Existing reading/card/disclosure choices remain.

All compiled blocks have a real card surface for their independently chosen material. Material guidance describes grouping, edge contrast and depth for that source surface; a button or input is not required. Global theme color/typography and block material are separate automatic axes; saved manual locks still constrain them. Theme option metadata does not turn a default material into a model constraint.

Chart options carry a source-bound mapping for the actual chart type, categories, series, source rows/columns, units and qualifications, including excluded totals or fields. Chart-note extraction recognizes Markdown headings, supported numbered bold headings and subsequent independent list-led blocks. Explicit table-note lists and following table-note paragraphs remain local; adjacent scenario/example qualifications and comparison prohibitions remain effective. This is a structural boundary rule, not general natural-language topic segmentation. An explicit `CAD 百万` header keeps both currency and scale without conversion; unsupported currency scales are declined. No chart is required merely because a legal mapping exists.

The new organization adapters remain experimental. The shared chart-note parser correction applies to both the experimental and nonexperimental routes; switching off the experiment retains the old routing and excludes the new organization choices, but does not restore the chart-note bug. Chart point/example payloads are sampled with explicit counts (currently eight examples); complete source coordinates remain. This is not a fixed upper bound for every note, plan or request.
