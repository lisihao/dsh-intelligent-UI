# Canvas UI and intelligent UI integration

## Scope agreed with the owner

The independent DSH intelligent UI plugin must give DSH frontend work reusable UI-development capabilities, automatically compose eligible assistant/tool/generated content, and support technical insight, coding, project management and quantitative research. The target is all 35 Canvas UI components in the pinned upstream catalog, including Ink Object and ASCII effects. Catalog presence, an automatic decision, a working native effect and production availability are recorded separately; a plain-content fallback is not counted as effect support.

The preceding design discussion was reviewed by the owner, who directed implementation and required compatibility with the upstream license. The official desktop application and other plugins remain unmodified. Takeover remains opt-in; original content, data, units, provenance and the single conversation display selector remain accessible. Rendering creates no model call or trading/benchmark action.

## Reference and integration boundary

- Repository: https://github.com/DavidHDev/canvas-ui ; inspected commit `a04a99b235299ee79a123a16ccb2e6cf9da74b6b`.
- Upstream license: MIT plus Commons Clause, https://github.com/DavidHDev/canvas-ui/blob/a04a99b235299ee79a123a16ccb2e6cf9da74b6b/LICENSE.md. It distinguishes embedding in a product from redistribution of the components themselves. Preserve copyright/license and do not place the component sources or ported components in a separately redistributed component library. Distribution of any product embedding is subject to the exact upstream terms; do not relabel upstream code MIT-only.
- Upstream source was inspected read-only in a separate scratch checkout; no upstream install/build/test scripts were run during analysis.
- Upstream publishes shadcn registry entries for its source components. Object effects use three.js; HTML effects capture live HTML through HTML-in-Canvas. WebGL and WebGPU variants have separate runtime requirements. The target DSH client currently uses React 18; upstream describes React 19 support, so the precise adapter must be verified rather than assumed.
- Existing UI code owns `conversation.chat.node`, `conversation.view`, output presentation and `solarExperienceUi`; styles and slot registrations are disposable. Unknown foreign pages and cross-origin surfaces have no general replacement seam. They can consume a new additive public document renderer, but compatibility styling alone is not a claim that their business views use it.
- Pinned OpenUI, ELK and React Flow remain the existing text/chart/graph dependencies. New third-party dependencies must be pinned and their licenses preserved; no copied upstream DSH source or runtime monkey patches.

## Architecture

1. A source catalog identifies all 35 upstream effects and their factual input/backend requirements, links and version. Catalog metadata must not be presented as executable capability.
2. An additive, disposable client rendering service exposes a session-independent document view with identity, value, raw source, provenance and controlled visual/raw/compare mode. It reuses the current UI-owned renderer and theme instances, makes no model request and never fabricates a session or alters source data.
3. A bounded automatic planner evaluates the source's semantic structure, available real assets, domain hints, theme and runtime capability. It selects only effects/providers that actually registered and are supported by the current host. Record enough information to replay its decision; missing providers fall back visibly to the existing source-preserving presentation.
4. Effect implementations are loaded behind registered, disposable providers. Availability, input compatibility, browser support and actual execution must be checked independently. Never load unverified executable code from arbitrary model output, theme packages or an external URL.
5. DSH frontend work uses model-invocable discovery and source guidance under its existing authorization. A reference to the upstream public documentation/registry is metadata, not redistribution of the component source. Reuse existing Uiverse development tools and design system where appropriate.
6. Domain views use actual source-backed structures: evidence and conditions for insight, code changes/test events for coding, ordered task records for project management, and timestamped price/NAV/drawdown series for quantitative work. Do not invent causality, numeric values, model objects, execution state, trading results or time/units.

## Delivery and acceptance

Current goal is full component support, not a catalog-only demonstration. For each component separately record reference version, input, registration, executable source/license distribution route, backend, interaction, automatic selection and installed-app result. Compatibility fallbacks remain explicitly pending for the effect until the actual result works.

Test the real normal DSH path and public SDK, source/raw equality, supported types, streaming, user theme, reduced motion, keyboard and error paths, repeat mount/disposal, capability failure, meaningful long data, and plugin disable/uninstall. Native acceptance/installation belongs to the authorized centralized installation session; development uses disposable profiles. The currently configured artifact byte/count limits remain explicit. Never put private screenshots, reports, account data or runtime receipts in Git.

## Open technical evidence

The installed DSH Electron 44 line uses Chromium 152, while Chrome's general HTML-in-Canvas stable guidance concerns Chrome 157; the actual DSH APIs and configuration require direct observation. If an upstream effect or distribution route is incompatible, record the exact failing component/condition, preserve the full target and pursue an upstream-compatible route rather than treating an unsupported fallback as completion.

At this fixed commit, all 35 upstream WebGL sources compiled in an isolated source-fetch/build experiment. All six object effects rendered a public CC0 GLB in an isolated Chromium; Ink and ASCII also rendered SVG and responded to pointer drag. Asciify and ASCII Sweep used upstream's approximate DOM-snapshot fallback without HTML-in-Canvas, but the tested code-reading lens was too faint or obscured text and is not enabled automatically. A separate MIT-licensed html2canvas experiment rendered Shatter and Cloth on decorative content without changing the upstream component. Its snapshot can distort numeric data, obscure text or disagree with interactive hit targets. A scratch-only conversion of simple `oklch(...)` values to RGBA worked for the tested OpenUI card, but gradients, SVG, wide-gamut and cross-origin resources remain unverified. The library's document-wide clone can also trigger extra resource loads, so that adapter is not enabled in this candidate. Particle Scroll additionally requires a real canvas subtree whose layout was zero in the fallback test. These experiments are not proof that the 29 HTML effects are automatically supported, and no temporary screenshots or upstream component source are committed.

A second scratch experiment used MIT-licensed `modern-screenshot@4.7.0` on a controlled, non-interactive subtree with font fetching disabled and external-resource requests explicitly rejected. The tested card's geometry and background color matched while Shatter and Cloth produced visible effects; no unrelated lazy image request was observed. Text/edge antialiasing still differed, and custom fonts, complex CSS, SVG, interaction and Desktop Chromium 152 remain unverified. It is not a runtime dependency or an enabled production adapter in this candidate.

The candidate's source-aware automatic path currently handles explicitly identified GLB records. A source-declared domain selects Ink, ASCII or Glass; otherwise Ink is used. Dithered remains available to developers but is not automatically selected because the tested dark and light presentations did not provide sufficient contrast. The public factory loader can request any catalog WebGL effect, but each consumer must supply appropriate elements, options and cleanup. Availability, visual fidelity and native interaction remain separate from successful compilation. Desktop installation and `dsh-app://` module loading are pending centralized acceptance.

A disposable DSH Web Host and isolated Chromium exercised the built plugin's `DocumentView` with Khronos's public CC0 Lantern model (SHA-256 `a79458c4b02d695187a952f23a63b8bf278e7bc3d316a3c2a314f2d6974181f1`). The normal content path selected Ink, retained the source record and exposed rotation controls. Anonymous and non-owner route requests were refused; an owner loaded the compiled effect through the same-origin route. After unmount, the test observed the canvas removed, its temporary object URL revoked and WebGL deletion calls. In a separate disposable Web Host run, all 35 individual WebGL factories were obtained from verified upstream source, compiled and imported successfully; the observed compiler concurrency peaked at two and the associated processes exited. This is factory-loading evidence, not visual or automatic-selection acceptance for all 35. No model was called. Chromium reported SwiftShader software WebGL, so this is not proof of hardware acceleration or installed Desktop behavior. Private captures and scratch receipts remain outside Git.
